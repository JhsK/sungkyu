# PR 작성 가이드

이 레포에서 PR을 만들거나 본문을 고칠 때 따르는 규칙입니다. 목표는 리뷰어가 본문을 1분 안에 읽고, 무엇이 왜 바뀌었는지 아는 것입니다. 어떻게 바뀌었는지는 diff가 보여 줍니다.

## 제목

`type(scope): 한국어 요약` 형식으로 씁니다. scope는 바뀐 영역이 하나일 때만 붙입니다.

- type은 `feat`, `fix`, `refactor`, `style`, `docs`, `chore`, `build` 중 하나입니다.
- 요약은 사용자나 개발자가 알아챌 변화로 씁니다.

```
feat(header): 시안 A 헤더와 다크 모드 토글 구현
docs: 블로그 시안 A와 디자인 인스펙터 추가
```

## 본문 구조

아래 순서를 지킵니다. 필수가 아닌 섹션은 쓸 내용이 있을 때만 넣습니다.

| 섹션            | 필수   | 내용                                    |
| --------------- | ------ | --------------------------------------- |
| `## 개요`       | 예     | 무엇을 하는 PR인지, 왜 필요한지 1~2문장 |
| `## 변경 사항`  | 예     | 사용자나 개발자가 알아챌 변화           |
| `## 범위 밖`    | 아니오 | 일부러 하지 않은 것과 그 이유           |
| `## 알아 둘 점` | 아니오 | 감수한 단점, 리뷰어가 판단해야 할 결정  |
| `## 확인`       | 예     | 확인한 것과 확인하지 않은 것            |

## 쓰는 법

- 동작과 결과를 씁니다. 클래스 이름, 훅 이름, CSS 값, 함수 시그니처처럼 diff에서 바로 보이는 내용은 쓰지 않습니다.
- 리뷰어가 알아야 판단할 수 있는 구현 결정은 예외입니다. 새 공용 컴포넌트나 앞으로 지켜야 할 규칙이 여기에 해당하고, 이름을 한 번 적고 이유를 한 문장으로 씁니다.
- 항목 하나는 한두 문장으로 씁니다. 하위 목록은 만들지 않습니다.
- 커밋 목록, 커밋 해시, 작업 과정은 쓰지 않습니다.
- `## 확인`에는 무엇을 확인했는지만 한 줄씩 씁니다. 측정 로그, 수치 표, 재현 절차는 넣지 않습니다. 확인하지 않은 것도 적습니다.
- 확인한 시점 이후에 코드가 바뀌었다면 그 사실을 적습니다.
- 섹션 제목을 포함해 30줄 안팎을 넘기지 않습니다. 넘는다면 PR을 나눌 수 있는지 먼저 봅니다.

## 리뷰 중 본문 갱신

push로 PR의 동작이 바뀌면 본문도 같이 고칩니다. 지운 기능이나 되돌린 결정이 본문에 남아 있으면 안 됩니다.

## 예시

```markdown
## 개요

블로그 시안 A의 헤더를 실제 앱에 옮기고 다크 모드 토글을 추가합니다. 기존 헤더는 시안과 크기, 색, 동작이 달랐습니다.

## 변경 사항

- 헤더를 시안대로 다시 만들고 모든 페이지에 표시합니다. 스크롤해도 상단에 고정되고, 현재 메뉴를 강조합니다.
- 다크 모드 토글을 추가합니다. 선택한 테마는 브라우저에 저장되고, 새로고침해도 깜빡임 없이 유지됩니다.

## 범위 밖

- 검색 버튼은 표시만 합니다. 검색할 글 데이터가 아직 없습니다.

## 알아 둘 점

- 다크 모드로 저장한 사용자는 페이지가 로드되는 동안 해 아이콘 대신 달 아이콘을 잠깐 봅니다. 배경색은 처음부터 다크로 나옵니다.

## 확인

- 빌드, 타입 체크, lint가 통과했습니다.
- Chrome에서 테마 토글과 새로고침 후 유지를 확인했습니다. Safari와 Firefox는 확인하지 않았습니다.
```
